LAB 08

API Gateway Sederhana (Node.js / Cloudflare Workers)

Menyatukan service-service dalam sistem proyek kelompok Anda di balik satu pintu masuk, lengkap dengan routing, pembatasan laju request (rate limiting), dan pengecekan API key. Tanpa Docker: gateway ditulis dengan Node.js yang sudah Anda kenal dari Backend Programming.

Durasi 100 menit
Format Praktikum Berkelompok
Terkait Proyek Lintas Mata Kuliah (kick-off sesi 08 kuliah)
Kaitan dengan proyek: Lab ini dikerjakan langsung di atas sistem proyek kelompok Anda (topik A–E), bukan contoh terpisah. Gateway yang Anda bangun menjadi komponen wajib arsitektur proyek. Konsep API Gateway dibahas di kuliah sesi 09, tetapi lab ini boleh dimulai lebih dulu karena yang dikerjakan hanya konfigurasi dasar. Karena gateway di sini berupa aplikasi Node.js biasa, ia bisa di-deploy ke Render seperti server GraphQL di lab 04.
Tujuan Pembelajaran
  • 01Mahasiswa mampu menjelaskan peran API Gateway sebagai pintu masuk tunggal untuk beberapa service.
  • 02Mahasiswa mampu membangun gateway Node.js yang meneruskan (proxy) request ke dua service berdasarkan path.
  • 03Mahasiswa mampu menerapkan rate limiting di gateway dan membuktikan efeknya.
  • 04Mahasiswa mampu menerapkan pengecekan API key sederhana di gateway.
Gambaran Arsitektur

Dari Banyak Alamat Menjadi Satu Alamat

Klien (browser / Postman / aplikasi lain) │ ▼ GATEWAY (Node.js) :8080 ← satu-satunya alamat yang diketahui klien ├─ rate limit (maks. 20 request / 10 detik per IP) ├─ cek API key (opsional) └─ routing /service-a/* → localhost:3000 /service-b/* → localhost:3001 │ ┌────┴─────┐ ▼ ▼ service-a service-b

Klien tidak perlu tahu ada berapa service di belakang, atau di port berapa masing-masing berjalan. Perubahan di belakang gateway tidak memaksa klien ikut berubah.

Langkah Praktik — Opsi A (Wajib)

Gateway dengan Node.js & Express

01

Siapkan Struktur Folder & Dependensi

proyek-kelompok/ ├── gateway/ # project baru untuk gateway ├── service-a/ # service pertama (jalan di port 3000) └── service-b/ # service kedua (jalan di port 3001)

Ganti service-a dan service-b dengan nama service sesuai topik kelompok Anda (misalnya booking dan inventory). Lalu di folder gateway:

npm init -y npm install express http-proxy-middleware express-rate-limit
02

Tulis gateway.js (Rate Limiting + Routing)

const express = require('express'); const { createProxyMiddleware } = require('http-proxy-middleware'); const { rateLimit } = require('express-rate-limit'); const app = express(); app.set('trust proxy', 1); // diperlukan saat di-deploy di balik proxy (mis. Render) // rate limit: maks. 20 request per 10 detik per alamat IP app.use(rateLimit({ windowMs: 10 * 1000, limit: 20, standardHeaders: true, legacyHeaders: false, })); // routing: /service-a/* diteruskan ke service-a app.use(createProxyMiddleware({ pathFilter: '/service-a', target: process.env.SERVICE_A_URL || 'http://localhost:3000', changeOrigin: true, pathRewrite: { '^/service-a': '' }, })); // routing: /service-b/* diteruskan ke service-b app.use(createProxyMiddleware({ pathFilter: '/service-b', target: process.env.SERVICE_B_URL || 'http://localhost:3001', changeOrigin: true, pathRewrite: { '^/service-b': '' }, })); app.use((req, res) => res.status(404).json({ error: 'Route tidak ditemukan' })); app.listen(process.env.PORT || 8080, () => console.log('Gateway berjalan'));

pathRewrite membuang prefix /service-a sebelum meneruskan: request ke /service-a/products sampai di service sebagai /products. Contoh ini memakai http-proxy-middleware versi 3.x (yang ikut terpasang saat npm install).

03

Jalankan Tiga Proses & Uji Routing

Buka tiga terminal: jalankan service-a di port 3000, service-b di port 3001 (sesuai cara masing-masing service mengatur port), lalu gateway:

node gateway.js

Di Postman, kirim request ke http://localhost:8080/service-a/... dan http://localhost:8080/service-b/.... Kedua service kini diakses lewat satu port, tanpa klien perlu tahu port aslinya.

04

Buktikan Rate Limiting

Buat file test-rate-limit.js (jalan di semua sistem operasi, memakai fetch bawaan Node.js 18+):

(async () => { for (let i = 1; i <= 30; i++) { const res = await fetch('http://localhost:8080/service-a/'); console.log(i, res.status); } })();

Jalankan dengan node test-rate-limit.js. Hasil yang diharapkan: 20 request pertama berstatus 200 (atau status normal service Anda), lalu sisanya 429 (Too Many Requests). Ambil screenshot output ini sebagai bukti. Jika service Anda tidak punya route /, ganti URL ke endpoint yang valid.

05

Tantangan Tambahan: Cek API Key di Gateway OPSIONAL

Terapkan konsep API key dari kuliah sesi 08: tolak request ke /service-b yang tidak membawa header X-API-Key yang benar. Tambahkan sebelum blok proxy /service-b:

const requireApiKey = (req, res, next) => { if (!process.env.API_KEY || req.get('X-API-Key') !== process.env.API_KEY) { return res.status(401).json({ error: 'Unauthorized' }); } next(); }; app.use('/service-b', requireApiKey);

Jalankan gateway dengan environment variable API_KEY terisi, lalu uji di Postman dengan dan tanpa header tersebut (200 vs 401). Simpan nilai key di environment variable atau file .env yang tidak di-commit ke GitHub, bukan di kode.

06

Deploy Gateway ke Render OPSIONAL

Jika kedua service sudah di-deploy dan punya URL publik, gateway bisa ikut di-deploy seperti server GraphQL di lab 04: push folder gateway ke GitHub, buat "New Web Service" di Render, atur start command node gateway.js, dan isi environment variable SERVICE_A_URL, SERVICE_B_URL, serta API_KEY. Hasilnya adalah satu URL publik untuk seluruh sistem, yang akan sangat membantu kelompok penguji saat code freeze.

Langkah Praktik — Opsi B (Alternatif)

Gateway di Edge dengan Cloudflare Workers

Berguna jika Anda ingin gateway yang langsung bisa diakses publik tanpa menjalankan server sendiri. Worker meneruskan request ke service yang sudah di-deploy (misalnya di Render atau Vercel) berdasarkan path.

A

Buat Proyek Worker

npm create cloudflare@latest gateway-kelompok # pilih template "Hello World" (Worker only), JavaScript
B

Tulis Logika Routing

export default { async fetch(request, env) { const url = new URL(request.url); // pengecekan API key sederhana if (request.headers.get('X-API-Key') !== env.API_KEY) { return new Response('Unauthorized', { status: 401 }); } const routes = { '/service-a': env.SERVICE_A_URL, '/service-b': env.SERVICE_B_URL, }; for (const [prefix, origin] of Object.entries(routes)) { if (url.pathname.startsWith(prefix)) { const target = origin + url.pathname.slice(prefix.length) + url.search; return fetch(new Request(target, request)); } } return new Response('Not found', { status: 404 }); } };
C

Atur Variabel & Deploy

Isi SERVICE_A_URL dan SERVICE_B_URL (URL deployment service Anda, tanpa garis miring di akhir) di bagian [vars] pada konfigurasi Wrangler. Simpan API key sebagai secret, bukan di file:

npx wrangler secret put API_KEY npx wrangler deploy

Uji dengan Postman: kirim request ke URL *.workers.dev dengan dan tanpa header X-API-Key, lalu bandingkan hasilnya (200 vs 401). Rate limiting di Cloudflare mengikuti fitur dan paket akun, sehingga bukti rate limiting di lab ini cukup diambil dari Opsi A.

Kesalahan Umum
Masalah yang Sering Muncul
Error proxy / 504 Gateway Timeout

Gateway tidak bisa menjangkau service di belakangnya. Periksa apakah service benar-benar sedang berjalan, port-nya sama dengan yang tertulis di target, dan (saat di-deploy) nilai SERVICE_A_URL/SERVICE_B_URL sudah benar.

404 dari service padahal route gateway sudah benar

Biasanya pathRewrite terlewat, sehingga prefix /service-a ikut diteruskan dan service tidak mengenali path-nya.

Request POST/PUT menggantung (tidak pernah selesai)

Jangan memasang app.use(express.json()) sebelum middleware proxy. Body request akan terbaca habis di gateway sehingga tidak sampai ke service. Parsing body cukup dilakukan di service masing-masing.

Rate limit tidak terpicu, atau semua pengguna terkena limit sekaligus setelah di-deploy

Untuk yang pertama, pastikan request dikirim cukup cepat dan beruntun (pakai skrip uji). Untuk yang kedua, pastikan app.set('trust proxy', 1) terpasang agar gateway membaca IP klien yang sebenarnya, bukan IP proxy milik platform hosting.

Checklist Kesiapan
  • Dua service sistem kelompok diakses lewat satu port gateway (8080), bukan port masing-masing
  • Rate limiting terbukti: output skrip uji menampilkan status 429 setelah batas terlampaui
  • Gateway bisa dijalankan dengan node gateway.js dan URL service dibaca dari environment variable
  • Secret (API key, URL database) tidak ada di repository
  • (Opsional) Pengecekan API key bekerja: 401 tanpa header, 200 dengan header benar
