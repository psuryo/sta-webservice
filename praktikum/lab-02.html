Konsep Singkat

Anatomi SOAP

SOAP (Simple Object Access Protocol) adalah protokol berbasis XML untuk bertukar informasi antar sistem. Setiap pesan SOAP dibungkus dalam struktur Envelope yang terdiri dari tiga bagian:

  • Header (opsional) — metadata seperti autentikasi, versi, atau instruksi routing.
  • Body (wajib) — isi pesan: nama operasi yang dipanggil beserta parameternya, atau hasil response.
  • Fault (di dalam Body, jika gagal) — kode dan pesan error yang dikembalikan server.

Kontrak layanan SOAP didefinisikan dalam file WSDL (Web Services Description Language) — dokumen XML yang mendeklarasikan operasi apa saja yang tersedia, tipe data yang diterima/dikembalikan, dan URL endpoint yang harus dituju.

Konteks historis: SOAP populer di era 2000-an untuk integrasi sistem enterprise (perbankan, pemerintah, ERP). Sebagian besar sistem baru kini memakai REST atau GraphQL, tetapi memahami SOAP tetap relevan karena banyak layanan lama masih aktif dan perlu diintegrasikan.
Langkah Praktik — Bagian A: Request & Response Normal

Eksplorasi SOAP Endpoint Publik

01

Buka dan Baca File WSDL

Buka URL WSDL berikut di browser. Ini adalah layanan kalkulator SOAP publik yang disediakan untuk keperluan belajar:

# buka di browser untuk melihat kontrak layanan https://www.dneonline.com/calculator.asmx?WSDL

Identifikasi elemen-elemen berikut di dalam file WSDL:

  • Tag <wsdl:operation> — nama operasi yang tersedia (Add, Subtract, Multiply, Divide)
  • Tag <wsdl:input> dan <wsdl:output> — nama message untuk setiap operasi
  • Tag <soap:address location="..."> — URL endpoint yang akan dituju saat mengirim request
02

Susun dan Kirim SOAP Request

Buat request baru dengan konfigurasi berikut:

  • Method: POST
  • URL: https://www.dneonline.com/calculator.asmx
  • Header: Content-Type: text/xml; charset=utf-8
  • Header: SOAPAction: "http://tempuri.org/Add"

Isi body (raw/XML) dengan envelope berikut — operasi penjumlahan 7 + 3:

<?xml version="1.0" encoding="utf-8"?> <soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/" xmlns:tns="http://tempuri.org/"> <soap:Body> <tns:Add> <tns:intA>7</tns:intA> <tns:intB>3</tns:intB> </tns:Add> </soap:Body> </soap:Envelope>

Kirim request dan verifikasi hasilnya — hasil penjumlahan muncul di dalam tag <AddResult>.

03

Coba Tiga Operasi Lain (Subtract, Multiply, Divide)

Ulangi langkah 02 untuk tiga operasi sisanya. Sesuaikan nilai SOAPAction dan nama tag operasi di dalam Body:

# contoh untuk Multiply — kalikan 6 × 4 # Header SOAPAction: "http://tempuri.org/Multiply" <tns:Multiply> <tns:intA>6</tns:intA> <tns:intB>4</tns:intB> </tns:Multiply>
Langkah Praktik — Bagian B: Simulasi SOAP Fault

Memancing dan Membaca Error

SOAP Fault adalah mekanisme resmi untuk melaporkan kegagalan — berbeda dengan REST yang mengandalkan HTTP status code. Struktur Fault selalu ada di dalam <soap:Body> dan memiliki empat elemen standar: faultcode, faultstring, faultactor, dan detail.

04

Kirim Request dengan Tipe Data Salah

Ganti nilai intA dengan string teks, lalu kirim request:

<tns:Add> <tns:intA>halo</tns:intA> <tns:intB>3</tns:intB> </tns:Add>

Amati response — apakah server mengembalikan SOAP Fault atau tetap memberikan hasil? Catat nilai faultcode dan faultstring yang diterima.

05

Kirim Request dengan Tag Salah (Typo pada Operasi)

Ganti nama tag operasi dengan nama yang tidak ada di WSDL:

# nama operasi ini tidak terdaftar di WSDL <tns:Tambah> <tns:intA>7</tns:intA> <tns:intB>3</tns:intB> </tns:Tambah>

Bandingkan faultcode yang diterima dengan percobaan sebelumnya — apakah kodenya berbeda?

06

Kirim Request dengan Namespace Salah

Ubah namespace tns ke URL yang keliru, lalu kirim:

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/" xmlns:tns="http://wrong-namespace.example/"> <soap:Body> <tns:Add> <tns:intA>7</tns:intA> <tns:intB>3</tns:intB> </tns:Add> </soap:Body> </soap:Envelope>

Catat perbedaan perilaku server — apakah server menolak, mengabaikan, atau memberikan hasil yang tidak terduga?

07

Dokumentasikan Pola Fault yang Ditemukan

Dari ketiga percobaan di atas, isi tabel berikut di catatan masing-masing (bisa di Markdown, Notion, atau kertas):

  • Jenis kesalahan yang dibuat
  • HTTP status code yang dikembalikan (200? 500?)
  • Nilai faultcode dan faultstring
  • Apakah error terdeteksi di level HTTP atau di dalam XML body?

Observasi terakhir penting: SOAP sering mengembalikan HTTP 200 meskipun operasinya gagal — error "disembunyikan" di dalam XML. Ini berbeda dengan REST yang memakai HTTP 4xx/5xx untuk menandai kegagalan.

Langkah Praktik — Bagian C: Perbandingan SOAP vs REST

Operasi yang Sama, Protokol Berbeda

Untuk memperkuat pemahaman, lakukan operasi yang setara menggunakan REST API publik, lalu bandingkan pengalamannya secara langsung.

08

Kirim Request REST yang Setara

Gunakan API matematika publik berikut untuk operasi penjumlahan yang sama (7 + 3):

# GET request — tidak perlu body, tidak perlu header khusus GET https://api.mathjs.org/v4/?expr=7%2B3

Bandingkan apa yang diperlukan: header, body, format data, dan panjang request dibanding SOAP untuk operasi yang sama persis.

09

Checklist Kesiapan
  • File WSDL kalkulator berhasil dibuka dan empat operasi berhasil diidentifikasi
  • Request SOAP untuk keempat operasi (Add, Subtract, Multiply, Divide) berhasil dikirim dan hasilnya benar
  • Tiga jenis SOAP Fault berhasil dipancing dan struktur faultcode/faultstring-nya dicatat
  • Perbedaan pelaporan error SOAP (HTTP 200 + Fault di body) vs REST (HTTP 4xx/5xx) mampu dijelaskan
  • Request REST yang setara berhasil dikirim dan tabel perbandingan sudah diisi berdasarkan pengamatan langsung
