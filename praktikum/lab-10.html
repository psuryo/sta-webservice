LAB 10

Komunikasi Antar Service via Message Queue

Menambahkan komunikasi asinkron pada toko dari lab 09: order-service menerbitkan event, notification-service mengonsumsinya lewat RabbitMQ. Anda akan melihat sendiri apa yang terjadi saat consumer mati, saat ada dua consumer, dan saat pesan diproses dua kali.

Durasi maks. 2 jam
Format Praktikum Berkelompok
Prasyarat Lab 09 (toko), Docker (Lab 01), Node.js 18+
Kaitan dengan proyek: Di lab 09, order-service memanggil product-service secara sinkron: bila yang dipanggil mati, pemanggil ikut gagal. Untuk hal yang tidak harus selesai saat itu juga (kirim email, catat audit, update statistik), pola yang lebih tepat adalah event lewat antrean. UAS praktikum mensyaratkan komunikasi asinkron, jadi lab ini sekaligus menjadi bahan langsung untuk proyek kelompok. Teori lengkapnya ada di materi kuliah tentang komunikasi asinkron dan event-driven.
Tujuan Pembelajaran
  • 01Mahasiswa mampu menjalankan message broker (RabbitMQ) dan membaca status antrean di dashboard-nya.
  • 02Mahasiswa mampu membuat producer dan consumer yang saling terpisah dan dihubungkan oleh antrean.
  • 03Mahasiswa mampu menunjukkan bahwa antrean menahan pesan saat consumer mati dan memprosesnya setelah pulih.
  • 04Mahasiswa mampu menjelaskan acknowledgement, pengiriman ulang pesan, dan perlunya consumer yang idempotent.

Langkah Praktik

Dari Panggilan Langsung ke Event

01

Jalankan RabbitMQ

docker run -d --name rabbit -p 5672:5672 -p 15672:15672 rabbitmq:3-management

Tunggu sekitar 20 detik, lalu buka http://localhost:15672 (user guest, password guest). Lihat tab Queues: masih kosong. Port 5672 dipakai aplikasi, 15672 untuk dashboard. Jika Docker tidak bisa dipakai, buat instance gratis RabbitMQ di penyedia cloud dan isi alamatnya lewat environment variable AMQP_URL.

02

Buat notification-service (consumer)

cd toko && mkdir notification-service && cd notification-service npm init -y && npm install amqplib

Simpan sebagai notification-service.js. Consumer dibuat lebih dulu agar antreannya sudah terikat ke exchange sebelum ada event yang diterbitkan.

const amqp = require('amqplib'); const AMQP_URL = process.env.AMQP_URL || 'amqp://localhost'; const QUEUE = process.argv.slice(2).find(a => !a.startsWith('--')) || 'notification-queue'; const CRASH = process.argv.includes('--crash'); // dipakai di langkah 07 const processed = new Set(); // daftar messageId yang sudah diproses (memori) async function main() { const conn = await amqp.connect(AMQP_URL); const ch = await conn.createChannel(); await ch.assertExchange('orders', 'fanout', { durable: true }); await ch.assertQueue(QUEUE, { durable: true }); await ch.bindQueue(QUEUE, 'orders', ''); ch.prefetch(1); // satu pesan per consumer pada satu waktu console.log(`[${QUEUE}] menunggu pesan...`); ch.consume(QUEUE, async (msg) => { if (!msg) return; let event; try { event = JSON.parse(msg.content.toString()); } catch { console.error('pesan rusak, dibuang'); return ch.nack(msg, false, false); } const id = msg.properties.messageId; if (processed.has(id)) { console.log('duplikat, dilewati:', id); return ch.ack(msg); } await new Promise(r => setTimeout(r, 1000)); // simulasi kirim email (1 detik) console.log(`[${QUEUE}] email terkirim: pesanan #${event.data.id} ${event.data.productName} x${event.data.qty}`); processed.add(id); if (CRASH) { console.log('crash sebelum ack!'); process.exit(1); } ch.ack(msg); // beri tahu broker: selesai, boleh dihapus }); } main().catch(e => { console.error(e.message); process.exit(1); });

Jalankan node notification-service.js. Di dashboard, tab Queues kini menampilkan notification-queue dan tab Exchanges menampilkan orders.

03

Tambahkan Publisher di order-service

cd ../order-service && npm install amqplib

Pada order-service.js, tambahkan kode berikut di bawah deklarasi orders:

const amqp = require('amqplib'); const AMQP_URL = process.env.AMQP_URL || 'amqp://localhost'; let channel = null; async function connectQueue() { try { const conn = await amqp.connect(AMQP_URL); conn.on('error', () => {}); conn.on('close', () => { channel = null; setTimeout(connectQueue, 3000); }); channel = await conn.createChannel(); await channel.assertExchange('orders', 'fanout', { durable: true }); console.log('terhubung ke RabbitMQ'); } catch (e) { console.error('RabbitMQ belum tersedia, coba lagi dalam 3 detik'); setTimeout(connectQueue, 3000); } } function publishOrderCreated(order) { if (!channel) { console.warn('channel tidak tersedia, event TIDAK terkirim:', order.id); return false; } const body = Buffer.from(JSON.stringify({ type: 'order.created', data: order })); return channel.publish('orders', '', body, { persistent: true, contentType: 'application/json', messageId: `order-${order.id}` }); }

Lalu panggil publishOrderCreated(order); tepat setelah orders.push(order); di handler POST /orders (sebelum res.status(201)...), dan panggil connectQueue(); sekali di dekat app.listen. Restart order-service.

04

Uji Alur Normal

Pastikan product-service, order-service, notification-service, dan gateway berjalan. Jalankan node smoke-test.js dari lab 09 (atau POST /order-service/orders di Postman). Harapan: order dibalas 201 segera, dan beberapa detik kemudian terminal notification-service mencetak "email terkirim". Perhatikan bahwa balasan ke klien tidak menunggu pengiriman email.

05

Uji Decoupling: Consumer Mati

Matikan notification-service (Ctrl+C). Buat tiga order lagi. Semuanya tetap 201. Buka dashboard, tab Queues: kolom Ready pada notification-queue bernilai 3 (ambil screenshot). Nyalakan kembali notification-service: ketiga pesan diproses berurutan dan Ready kembali 0. Inilah keuntungan antrean: pengirim dan penerima tidak harus hidup bersamaan.

06

Dua Consumer: Berbagi Beban vs Pub/Sub

Competing consumers. Buka dua terminal, jalankan node notification-service.js di keduanya (antrean sama). Kirim 6 order beruntun: pesan dibagi di antara dua consumer.

Pub/Sub. Hentikan salah satunya, lalu jalankan node notification-service.js audit-queue (antrean berbeda, tetap terikat ke exchange orders). Kirim beberapa order: setiap antrean menerima salinan event yang sama. Catat perbedaan kedua perilaku ini.

07

Uji Pengiriman Ulang dan Idempotensi

Hentikan semua consumer lalu jalankan satu dengan node notification-service.js --crash. Kirim satu order: consumer mencetak "email terkirim" lalu mati sebelum ack. Di dashboard, pesan itu masih berstatus Ready/Unacked. Jalankan consumer biasa (tanpa --crash): pesan dikirim ulang dan email tercetak untuk kedua kalinya. Daftar processed hilang saat proses mati, sehingga duplikat tidak terdeteksi.

Kesimpulan: broker menjamin pesan setidaknya sekali sampai (at-least-once), bukan tepat sekali. Consumer harus idempotent, dan pencatatan "sudah diproses" harus disimpan di penyimpanan yang tahan restart (misalnya tabel database), bukan di memori.

08

Diagram, Commit & Bukti

Perbarui diagram arsitektur dari lab 09 dengan RabbitMQ, exchange, dan notification-service. Commit ke repository yang sama (folder notification-service dan perubahan di order-service, tanpa node_modules). Jangan menyimpan kredensial broker di repository; pakai environment variable AMQP_URL.

Kesalahan Umum
Masalah yang Sering Muncul
connect ECONNREFUSED 127.0.0.1:5672

RabbitMQ belum siap atau container mati. Cek docker ps dan tunggu sampai dashboard di port 15672 bisa dibuka. Jika port bentrok, hentikan container lama (docker rm -f rabbit).

Event tidak muncul di consumer padahal order berhasil

Pada exchange fanout, pesan yang diterbitkan saat belum ada antrean terikat langsung hilang. Jalankan consumer minimal sekali sebelum menerbitkan event.

PRECONDITION_FAILED - inequivalent arg 'durable'

Antrean atau exchange sudah ada dengan pengaturan berbeda. Hapus lewat dashboard (tab Queues/Exchanges), lalu jalankan ulang.

Pesan hilang setelah RabbitMQ di-restart

Pastikan exchange dan antrean durable: true dan pesan diterbitkan dengan persistent: true (sudah ada di kode).

Pesan terus berstatus Unacked

Consumer tidak memanggil ack atau nack pada semua jalur kode. Setiap pesan harus diakhiri dengan salah satunya.
