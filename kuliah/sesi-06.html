gRPC & Protocol Buffers

Setelah GraphQL menyelesaikan masalah fleksibilitas data untuk klien, sesi ini membahas pendekatan yang menyelesaikan masalah berbeda: performa komunikasi antar microservice.

Materi — Konsep RPC

Memanggil Fungsi di Mesin Lain Seolah Lokal

RPC (Remote Procedure Call) sebenarnya konsep yang jauh lebih tua dari REST — idenya sederhana: klien memanggil sebuah function/method di server, dan secara sintaks terasa seperti memanggil fungsi biasa di kode sendiri, walaupun sebenarnya eksekusinya terjadi di mesin lain lewat jaringan.

Bedanya dengan REST yang berpikir dalam resource (GET /products), RPC berpikir dalam aksi/method (GetProduct(), CreateOrder()) — mengingatkan kembali pada gaya pemanggilan SOAP di sesi 03, hanya saja gRPC jauh lebih ringan dan modern.

Materi — Protocol Buffers

Format Data Biner yang Jauh Lebih Ringkas

Alih-alih JSON berbasis teks, gRPC memakai Protocol Buffers (protobuf) — data diserialisasi menjadi format biner yang jauh lebih kecil dan cepat diproses. Skema-nya ditulis lebih dulu di file .proto (mirip semangat contract-first di WSDL/OpenAPI):

// product.proto syntax = "proto3"; message Product { int32 id = 1; string title = 2; float price = 3; } message ProductRequest { int32 id = 1; } service ProductService { rpc GetProduct(ProductRequest) returns (Product); }

Angka di belakang tiap field (= 1, = 2, dst) bukan nilai — itu adalah nomor posisi field dalam format biner, dipakai compiler protobuf untuk encoding/decoding yang efisien tanpa perlu mengirim nama field secara literal seperti JSON.

Materi — Kenapa Lebih Cepat

Protobuf vs JSON, dan HTTP/2 vs HTTP/1.1

AspekREST/GraphQL (JSON, umumnya HTTP/1.1)gRPC (Protobuf, HTTP/2)
Ukuran payloadLebih besar — nama field ditulis literal tiap kaliLebih kecil — field direpresentasikan sebagai nomor biner
ParsingParse teks ke objek (lebih lambat)Decode biner langsung ke struct (lebih cepat)
KoneksiHTTP/1.1: satu request per koneksi (umumnya)HTTP/2: multiplexing, banyak request paralel dalam satu koneksi
StreamingTidak didukung secara nativeDidukung native (lihat 4 model komunikasi di bawah)
Materi — Empat Model Komunikasi gRPC

Bukan Cuma Request-Response Biasa

Unary paling umum
Satu request, satu response — persis seperti REST/GraphQL biasa. Ini yang dipakai di lab 06.
Server Streaming
Satu request, server mengirim banyak response secara berturut-turut (mis. live update harga saham).
Client Streaming
Klien mengirim banyak request secara berturut-turut, server merespons sekali di akhir (mis. upload data batch).
Bidirectional Streaming
Klien dan server saling mengirim data kapan saja, dua arah sekaligus (mis. chat real-time, video call signaling).
Materi — Trade-off yang Harus Diketahui

gRPC Bukan Pengganti REST/GraphQL Secara Universal

  • Tidak bisa langsung dipanggil dari browser — perlu proxy tambahan (grpc-web) karena browser tidak mendukung kontrol HTTP/2 level rendah yang dibutuhkan gRPC.
  • Tidak human-readable — payload biner tidak bisa dibaca langsung seperti JSON di DevTools, menyulitkan debugging manual.
  • Tooling lebih kompleks — perlu compiler protobuf untuk generate kode dari file .proto, beda dari REST yang bisa langsung ditulis manual.

Karena itu, gRPC hampir selalu dipakai untuk komunikasi antar microservice internal (server-to-server), sementara REST/GraphQL tetap dipakai di lapisan yang menghadap klien (browser/mobile) — persis pola yang akan dibahas lebih lanjut di sesi 09 (API Gateway).

Diskusi Kelas
Studi Kasus

Project GraphQL Anda dari lab 04-05 (categories/products) saat ini mengakses database secara langsung dalam satu service. Bayangkan sistem ini berkembang: layanan pengecekan stok dipisah jadi service tersendiri, dan dipanggil ribuan kali per detik oleh service utama. Diskusikan: apakah komunikasi antara kedua service ini sebaiknya tetap pakai REST/GraphQL, atau beralih ke gRPC? Apa pertimbangannya?

Rangkuman
  • gRPC mengimplementasikan konsep RPC klasik dengan performa modern, berbasis Protocol Buffers dan HTTP/2.
  • Protobuf jauh lebih ringkas dari JSON/XML karena data direpresentasikan biner dengan nomor field, bukan nama field literal.
  • Empat model komunikasi gRPC (unary, server streaming, client streaming, bidirectional streaming) memberi fleksibilitas yang tidak dimiliki REST/GraphQL secara native.
  • gRPC unggul untuk komunikasi antar microservice berperforma tinggi, tapi tidak cocok dipanggil langsung dari browser — biasanya dikombinasikan dengan REST/GraphQL di lapisan yang menghadap klien.
