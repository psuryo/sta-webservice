SESI 09

API Gateway & Reverse Proxy

Anda sudah membangun gateway sederhana di lab 08. Sesi ini membedah apa sebenarnya yang Anda bangun, apa yang belum ada di dalamnya, dan keputusan apa yang perlu diambil saat gateway menjadi bagian arsitektur sungguhan.

Durasi 100 menit
Format Kuliah Tatap Muka
Terkait Lab 08 — API Gateway Sederhana
Kaitan dengan praktikum dan proyek: Materi ini membahas konsep di balik gateway yang sudah Anda tulis di lab 08 (routing, rate limiting, pengecekan API key). Gateway adalah komponen wajib arsitektur proyek, sehingga keputusan di sesi ini langsung masuk ke bagian 4.1 laporan Anda.
Tujuan Pembelajaran
  • 01Mahasiswa mampu membedakan reverse proxy, load balancer, dan API gateway beserta tumpang tindih di antaranya.
  • 02Mahasiswa mampu menjelaskan tanggung jawab umum sebuah API gateway dan mengenali mana yang sudah dikerjakan di lab 08.
  • 03Mahasiswa mampu menjelaskan pola gateway aggregation dan Backend for Frontend (BFF).
  • 04Mahasiswa mampu mengidentifikasi risiko gateway (single point of failure, bottleneck, gateway gemuk) beserta mitigasinya.
  • 05Mahasiswa mampu memutuskan tanggung jawab mana yang ditempatkan di gateway dan mana yang tetap di service.
Materi — Tiga Istilah yang Sering Tertukar

Reverse Proxy, Load Balancer, API Gateway

Load balancerMembagi trafik ke beberapa instance dari service yang samaSkalabilitas dan ketersediaanNginx, HAProxy, load balancer milik cloud
API gatewayPintu masuk yang memahami API: route, identitas klien, kuotaKebijakan tingkat API untuk banyak service sekaligusKong, Traefik, AWS API Gateway, gateway buatan sendiri (lab 08)

Batasnya kabur. Satu produk seperti Nginx bisa memerankan ketiganya, tergantung konfigurasinya. Bedanya terletak pada apa yang dipahami komponen itu: reverse proxy hanya melihat koneksi dan HTTP, sedangkan API gateway menerapkan aturan yang bermakna bagi API (siapa pemanggilnya, berapa kuotanya, service mana yang berhak menangani).

Materi — Dua Pola Penting

Gateway Aggregation dan Backend for Frontend

Gateway Aggregation

Satu request dari klien menghasilkan beberapa panggilan ke service di belakang, lalu hasilnya digabung menjadi satu respons. Misalnya halaman detail pesanan yang butuh data dari service pesanan, pembayaran, dan pengiriman: klien cukup satu kali memanggil, tidak tiga kali. Tujuannya sama dengan GraphQL di sesi 5 (mengurangi bolak-balik jaringan), hanya diselesaikan di sisi server.

Backend for Frontend (BFF)

Satu gateway per jenis klien: misalnya satu untuk aplikasi mobile, satu untuk dashboard web. Tiap gateway menyajikan data dalam bentuk yang paling pas untuk kliennya, tanpa memaksa satu API melayani kebutuhan yang berbeda-beda. Harganya, ada lebih banyak komponen yang harus dikelola.

Materi — Risiko dan Mitigasi

Pintu Masuk Tunggal Berarti Titik Rawan Tunggal

Risiko Utama
  • Single point of failure: jika gateway mati, seluruh sistem tidak bisa diakses meski semua service sehat.
  • Bottleneck: seluruh trafik lewat satu titik, sehingga kapasitasnya menentukan kapasitas sistem.
  • Gateway gemuk: logika bisnis perlahan menumpuk di gateway, membuatnya sulit diubah dan menjadi "monolith baru" di depan microservices.
  • Koordinasi perubahan: setiap route baru memerlukan perubahan di gateway, yang bisa memperlambat tim service.

Mitigasi umum: jalankan beberapa instance gateway di belakang load balancer (gateway dibuat stateless), jaga gateway tetap tipis (hanya urusan lintas-service seperti routing, kuota, autentikasi dasar), dan pantau kesehatannya secara aktif.

Jangan Hanya Mengandalkan Gateway

Kesalahan umum: service di belakang gateway sepenuhnya mempercayai bahwa semua request yang sampai pasti sudah diperiksa. Jika suatu hari service bisa dijangkau tanpa melewati gateway (konfigurasi jaringan salah, atau service ikut dibuka ke publik seperti saat Anda menjalankannya di port sendiri di lab 08), semua pemeriksaan itu terlewati. Praktik yang lebih aman adalah defense in depth: gateway memeriksa identitas di tepi, tetapi service tetap memverifikasi token dan menerapkan otorisasi spesifik bisnis (misalnya "hanya pemilik reservasi yang boleh membatalkannya"). Di sini mTLS antar service dari sesi 8 punya peran.

Diskusi Kelas
Aktivitas Kelompok

Untuk sistem proyek kelompok Anda, tentukan apakah tiap tanggung jawab berikut ditangani di gateway, di service, atau keduanya, beserta alasannya: (1) pemeriksaan token, (2) otorisasi per data (mis. hanya pemilik yang boleh mengubah), (3) rate limiting, (4) validasi input, (5) logging, (6) caching. Bandingkan hasil kelompok Anda dengan kelompok lain, lalu bahas perbedaannya.

Rangkuman
  • Reverse proxy, load balancer, dan API gateway saling tumpang tindih. Yang membedakan adalah seberapa jauh komponen itu memahami API.
  • Tanggung jawab umum gateway: routing, rate limiting, autentikasi di tepi, TLS termination, caching, dan logging terpusat. Tiga di antaranya sudah Anda praktikkan di lab 08.
  • Gateway aggregation mengurangi bolak-balik klien, dan BFF memberi satu gateway per jenis klien.
  • Gateway adalah titik rawan tunggal dan bisa menjadi gemuk. Jaga tetap tipis, jalankan lebih dari satu instance, dan jangan menjadikannya satu-satunya lapisan pemeriksaan.
Tugas & Latihan
Tugas Kelompok

Perluas rancangan keamanan awal dari sesi 08 menjadi rancangan gateway sistem kelompok Anda (1-2 halaman): (1) diagram arsitektur dengan gateway di depan service-service Anda, (2) tabel pembagian tanggung jawab "tanggung jawab → gateway/service/keduanya → alasan" hasil diskusi kelas, dan (3) satu paragraf tentang risiko single point of failure pada sistem Anda dan cara memitigasinya. Rancangan ini menjadi bahan bagian 4.1 laporan proyek. Dikumpulkan sebelum sesi 10.
