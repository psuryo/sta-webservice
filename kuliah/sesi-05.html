Materi — Masalah yang Diselesaikan GraphQL

Over-fetching & Under-fetching di REST

Bayangkan aplikasi mobile hanya butuh nama produk untuk ditampilkan di daftar, tapi endpoint REST /products tetap mengembalikan semua field:

OVER-FETCHING (REST)
GET /products [{ "id": 1, "title": "Kopi Arabika", "price": 75000, "description": "...", "stock": 120, "created_at": "..." }]

Klien cuma butuh title, tapi tetap menerima 6 field sekaligus — bandwidth terbuang, terutama kalau datanya ribuan baris.

Sebaliknya, kalau dashboard admin butuh data produk sekaligus nama kategorinya, REST biasa memaksa 2 request terpisah (under-fetching) — inilah yang GraphQL selesaikan lewat query tunggal seperti yang sudah Anda praktikkan di lab: klien meminta persis field yang dibutuhkan, termasuk relasi bersarang, dalam satu request.

Materi — Type System

Fondasi Schema Definition Language (SDL)

Scalar Type
Tipe dasar: String, Int, Float, Boolean, ID — tidak punya sub-field.
Object Type
Tipe yang Anda definisikan sendiri, seperti Category dan Product di lab 04 — wajib punya selection set saat di-query.
Non-Null (!)
Tanda seru menandakan field tidak boleh null — kalau resolver mengembalikan null untuk field ber-tanda ini, GraphQL akan melempar error.
List ([ ])
Menandakan field mengembalikan array, seperti [Product!]! yang berarti: list-nya sendiri tidak null, dan tiap itemnya juga tidak null.
Materi — Mekanisme Resolver

Bagaimana Resolver Benar-Benar Dieksekusi

Ini bagian yang paling penting untuk dipahami mendalam, karena langsung membedah kode yang sudah Anda tulis sendiri di lab 04:

1. Root Resolver Dipanggil Lebih Dulu

Saat query categories { ... } dijalankan, GraphQL memanggil resolver Query.categories terlebih dahulu — inilah yang mengambil semua baris dari tabel categories.

2. Setiap Item Hasil Diproses Lagi

Untuk tiap kategori yang dikembalikan, kalau query meminta field products, GraphQL memanggil resolver Category.products — dengan parameter parent berisi objek kategori yang sedang diproses.

3. Field parent Menyambungkan Antar Resolver

Persis di kode Anda: parent.id pada resolver Category.products dipakai untuk query WHERE category_id = $1 — inilah mekanisme yang menghubungkan data induk ke data anak.

4. Proses Berulang untuk Setiap Level Nested

Kalau schema punya relasi 3 tingkat, resolver akan dipanggil berlapis-lapis — inilah yang jadi akar dari masalah performa yang dibahas berikutnya.

Materi — Keterbatasan Penting: N+1 Problem

Fleksibilitas GraphQL Punya Harga

Ingat resolver Category.products yang Anda tulis di lab 04? Kalau ada 10 kategori dan klien meng-query categories { products { title } }, urutan query ke database sebenarnya adalah:

1x query: SELECT * FROM categories (ambil 10 kategori) 10x query: SELECT * FROM products WHERE category_id = ? (satu per kategori) Total: 11 query database untuk 1 request GraphQL
Ini yang disebut N+1 Problem

1 query untuk data induk, ditambah N query terpisah untuk tiap item anaknya. Untuk 10 kategori masih terasa ringan, tapi untuk 10.000 kategori, ini bisa jadi 10.001 query database dalam satu request — masalah performa serius yang tidak terlihat saat aplikasi masih kecil.

Solusi standarnya adalah DataLoader — library yang mengumpulkan (batch) semua permintaan category_id dalam satu siklus eksekusi, lalu menjalankannya sebagai satu query memakai WHERE category_id IN (...), bukan satu-satu. Implementasi detailnya di luar cakupan sesi ini, tapi penting untuk mengenali gejalanya sejak dini.

Diskusi Kelas
Aktivitas: Audit Kode Sendiri

Buka kembali resolver relasi (yang menghubungkan tabel induk-anak, sejenis Category.products) dari project lab 04 Anda sendiri. Diskusikan dengan kelompok: kalau tabel induk pada project Anda punya 5.000 baris, berapa kali query database akan dijalankan saat klien meng-query semua data induk beserta relasinya sekaligus? Apakah kode Anda saat ini rentan terhadap N+1 Problem?

Rangkuman
  • GraphQL mengatasi over-fetching dan under-fetching dengan membiarkan klien menentukan sendiri field dan relasi yang ingin diambil dalam satu query.
  • Type System GraphQL (scalar, object, non-null, list) membentuk kontrak yang ketat secara tipe, mirip yang sudah Anda tulis di typeDefs.
  • Resolver dieksekusi berlapis: resolver root dulu, lalu resolver field relasi dipanggil untuk tiap item, dengan parent sebagai penghubung.
  • Fleksibilitas ini punya harga: N+1 Problem bisa muncul diam-diam pada resolver relasi yang query database satu per satu, dan solusinya (DataLoader) bekerja dengan cara batching query.
Tugas & Latihan
Latihan Mandiri

Tambahkan variabel counter (misal let resolverCallCount = 0;) di resolver relasi pada project GraphQL Anda sendiri dari lab 04/05 — bukan harus resolver Category.products, sesuaikan dengan nama tabel/relasi yang benar-benar ada di project kelompok Anda. Tambahkan increment counter setiap kali resolver tersebut dipanggil, lalu tampilkan nilainya (misalnya lewat console.log di terminal server, atau field tambahan sementara di response). Jalankan query yang mengambil seluruh data induk beserta relasinya sekaligus, lalu ambil screenshot hasil counter tersebut. Bandingkan dengan prediksi N+1 Problem: apakah jumlah pemanggilan resolvernya sesuai rumus 1 + N? Dikumpulkan sebelum sesi 06.
